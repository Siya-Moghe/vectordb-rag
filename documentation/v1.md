# Explanations — v1 checkpoint

What's here, why it's built this way, and what's deliberately missing.

## What works right now

```
Client → Collection → FlatIndex   (vectordb/)
              ↓
   chunker → embedder → pipeline → generator   (rag/)
```

Run `python demo.py` (after `pip install -e .` and setting `GEMINI_API_KEY`)
and it will: read `data/corpus/sample.txt`, chunk it, embed each chunk
locally, store the vectors in memory, then answer a question by retrieving
the most relevant chunks and calling Gemini.

## vectordb/

**`distance.py`** — three scoring functions (cosine, dot, euclidean), all
vectorized over a whole matrix at once instead of looping in Python. This
is the single biggest performance lever for brute-force search: numpy's
matrix multiply is BLAS-backed and orders of magnitude faster than a
Python `for` loop over vectors.

One subtlety worth knowing: cosine/dot are *similarity* (higher = better
match) but euclidean is *distance* (lower = better match). `metric_is_similarity()`
exists so the index code doesn't need to special-case each metric — it just
asks "does higher mean better here?" and sorts accordingly.

**`index/base.py`** — a `Protocol` (structural typing, not inheritance)
defining what any index must support: `build`, `add`, `remove`, `search`.
Nothing depends on this at runtime yet since there's only one index, but it
means when IVF gets added later, `Collection` won't need to change — it'll
just be handed a different object that satisfies the same shape.

**`index/flat.py`** — brute-force search. Every vector lives in one numpy
array; every search scores every vector. No shortcuts, no approximation.
This is intentional — it's the ground truth you'll benchmark IVF against
later ("did the approximate index find the same top-k as brute force?").
Uses `argpartition` instead of a full `argsort` to find the top-k, which is
O(n) instead of O(n log n) — matters once n is large.

**`collection.py`** — pairs an index with a plain Python dict for metadata
(e.g., chunk text, source filename). No SQLite yet, no persistence yet —
everything lives in RAM and disappears when the process exits. That's the
biggest limitation right now and the next thing to fix (see "What's missing").

The `filter` parameter in `search()` is a crude post-filter: it over-fetches
more candidates than requested, then throws away ones that don't match the
metadata filter. It works, but it's not efficient — a real implementation
would push the filter down before or during the ANN search, not after.

**`client.py`** — just a dict of `{name: Collection}`. The `path` argument
is accepted but unused; it's there so that once persistence is added,
`Client(path="./mydb")` won't require changing every call site that already
constructs a `Client`.

## rag/

**`chunker.py`** — splits text into overlapping windows by word count (not
real tokens — a real tokenizer would count differently, but word count is a
close enough proxy and needs zero extra dependencies). `overlap` exists so
a sentence that falls right on a chunk boundary still appears intact in at
least one chunk.

**`embedder.py`** — wraps `sentence-transformers`' `all-MiniLM-L6-v2`
(384-dim, ~80MB, CPU-only). The model loads lazily on first call and is
cached at module level, so importing this file costs nothing and you only
pay the load time once per process, not once per embed call.

**`generator.py`** — the only piece of this whole system that costs money
or needs the network. Deliberately isolated in one function (`generate()`)
so it's trivial to mock out in tests or swap providers later without
touching chunking/embedding/retrieval at all. Also isolates the Gemini
client as a lazy singleton, same pattern as the embedder.

**`pipeline.py`** — the actual glue. `ingest_text()` runs chunk → embed →
insert. `ask()` runs embed(question) → retrieve → generate(). Note that
`ask()` returns both the answer *and* the retrieved context — you want that
visible so you can sanity-check what the model actually saw, not just trust
the final answer.

## What's deliberately NOT here yet

- **Persistence.** Everything is in-memory. Restart the process, lose
  everything. This is next: a write-ahead log + snapshot file so you don't
  have to re-embed your whole corpus every time you run the script.
- **IVF index.** Flat/brute-force is fine until you have enough vectors
  that it's noticeably slow (tens of thousands+). Not worth building
  before you can feel the problem it solves.
- **Eval harness.** No recall@k / MRR / faithfulness scoring yet — that
  needs a labeled question set, which needs an actual corpus to write
  questions against first.
- **SQLite metadata store.** Currently a plain dict. Fine until you want
  to filter on metadata *before* scoring (not just after), or the metadata
  itself needs to survive a restart.

## Known rough edges

- `Collection.search()`'s `filter` is O(over-fetch) — inefficient at scale,
  fine for a personal corpus of a few hundred/thousand chunks.
- `Collection.insert()` upserts silently (same id = overwrite) with no
  warning. Fine for now, might bite you if you re-ingest a file and expect
  duplicates to be rejected instead.
- No batching/rate-limit handling on the Gemini calls — if you ingest a lot
  of text and later add Gemini-based embeddings or LLM-as-judge scoring,
  you'll want retry/backoff logic that doesn't exist yet.
